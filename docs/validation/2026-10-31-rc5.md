# 2026-10-31 验证：DSH 0.2.1-rc.5（@anweat/dsh-background 0.1.0，本地开发版）

> 文中提到的 `logs/`、`probe/` 原始日志与探针脚本不在本仓库中，保存在作者本机的实验目录。

结论：`background_run` 在 `@deepseek-ai/dsh@0.2.1-rc.5` 的真实宿主里按设计工作：起 job、立即返回、`job_list` / `job_output` / `job_kill` 可用、与回合 signal 脱钩、前置拒绝不登记 job、会话销毁时被中止并记 `killed`。同一套探针在 `0.2.0-rc.2` 上也通过。第二阶段（自动转后台）的三个问题没有全部满足，所以没有实现。

执行者是开发者侧代理，不是独立验证者。只写亲眼看到的结果。**没有跑任何模型会话**：完成通知唤醒空闲会话的那一轮、模型怎么读 skill 和提示、聊天界面怎么展示，都没有验证。

## 1. 环境与方法

- 宿主：`npm i --prefix <scratchpad> @deepseek-ai/dsh@0.2.1-rc.5 --registry https://registry.npmjs.org`（npmmirror 落后，没用）。另装 `@deepseek-ai/dsh@0.2.0-rc.2` 做第 4 节。
- 插件：`pnpm pack` 出 tgz（嵌套 pnpm 11.7.0，PATH 垫片），`dsh plugin --profile headless add <tgz>`。
- 隔离：全新 `DSH_HOME`（scratchpad 下），没有读写 `~/.dsh`，没有占用 19387（web 用 3401），没有碰桌面端，没有读凭据，没有跑模型。
- headless profile：关掉 `llm-deepseek`、`llm-deepseek-account`、`headless-runner`；`tool-jobs` 设 `completionDelivery: quiet`，空闲会话收到完成通知时只进收件箱、不开 follow-up turn，也就不会触发模型。
- 探针插件（`probe/`，不随包发布）在 `ready` 后 `ctx.agents.create()` 建一个空闲 agent（不发 prompt），再用宿主自己的 `ctx.tools.execute` 以该 agent 的身份调工具，自己注册 `probe_sleep` 等慢工具，订阅 `session/event` 看 `job/registered`、`job/settled` 和收件箱，结果写 JSON（样本在 `logs/`）。

## 2. 阶段一：真实宿主观察（rc.5，headless）

引号里是原样输出，id 每次运行不同。

**起 job**（`probe_sleep` 1.5 秒）：调用本身 5 到 100 毫秒返回（首次 100 ms 左右含加载，之后 2 到 8 ms）：

> `probe_sleep started in the background as job tool-56248664f150461c (sleep 1.5s (alpha)). A completion notice arrives when it finishes; read the result with job_output, stop it with job_kill. Do not wait or poll unless you need the result now.`

- `job_list`：`tool-56248664f150461c [tool] running — probe_sleep: sleep 1.5s (alpha)`
- `job_output`（不等）：`(no new output)\n[status: running, running probe_sleep]`（进度行就是插件写的 `running probe_sleep`）
- `job_output`（`wait: true`）1503 ms 后：`slept 1500ms (alpha)\n[status: completed]`
- 再读一次：`(no new output)\n[status: completed]`（结果只给一次）
- `job_list`：`... completed — probe_sleep: sleep 1.5s (alpha)`

**`job_kill`**（2 分钟的 job，300 ms 后）：`requested cancellation of job tool-...`；随后 `job_output`：`(no new output)\n[status: killed, probe kill]`；嵌套工具体的 signal 被中止；会话记录 `job/settled`：`status: killed, cause: kill, detail: probe kill`。

**与回合 signal 脱钩**：用调用方自己的 AbortController 的 signal 调 `background_run`，job 启动后把这个 controller 中止（模拟用户点停止）。嵌套工具体的 signal 没有被中止（`abortedDuring: []`），`job_list` 仍是 `running`，1200 ms 的工具照常 `completed`：`slept 1200ms (detached)\n[status: completed]`。

**失败**（`probe_fail` 抛错）：`job_output` → `Error: probe_fail: deliberate failure\nwith a second line\n[status: failed, probe_fail: deliberate failure]`。

**长结果**（50000 字符）：`job_output` 共 20057 字符，结尾 `… [truncated: 29930 more characters]\n[status: completed]`（`maxResultChars` 默认 20000）。

**前置拒绝**（全部 `INVALID_ARGS`，`job_list` 里没有多出 job）：

- 未知工具：`invalid arguments: tool "no_such_tool" is not available to this agent; use a name from your tool list`
- 自身：`invalid arguments: background_run cannot run itself in the background`
- `job_output`：`invalid arguments: job_output controls background jobs and cannot run in the background; call it directly`
- `bash`：`invalid arguments: bash has its own background mode; call it directly with run_in_background: true`
- `subagent`：`invalid arguments: subagent already runs in the background and reports through the job runtime; call it directly`
- `workflow`：`... workflow has its own background mode; call it directly with run_in_background: true`
- 目标参数错：`invalid arguments: probe_sleep: "arguments.ms" must be an integer`
- 缺 `description`：`invalid arguments: missing required property "description"`

**并发上限**（默认 4）：前四个成功，第五个：`invalid arguments: too many background tool jobs for this agent (4 of 4 running); wait for one to finish or stop one with job_kill`。逐个 `job_kill` 后四个都是 `killed`。

**完成通知**（没有人在 `wait`，job 自己结束）：收件箱（`agent/inbox/spliced`，target `next-step`，source `tool-jobs` / `notice`）收到：

> `background job tool-a10eb295b459482a (tool: probe_sleep: finishes unattended) finished [status: completed]. Read its output with job_output.`

随后 `job_output` 给结果 `slept 300ms (notice)\n[status: completed]`。所以通知**不带结果**，这也是工具返回文字和 README 写“读 `job_output`”的原因（brief 里的文字“result arrives with the completion notice”不准确，我改了，见下面“偏离”）。被 `job_output` 的 wait 收走的和被 `job_kill` 杀掉的 job 没有通知，符合宿主文档。

**会话记录**：每个 job 写 `job/registered` 和 `job/settled`，带 `toolCall: {callId: "probe-1", rootCallId: "probe-1"}`，`kind: "tool"`，`owner` 是 agent 的会话 id；settled 的 `cause` 分别是 `producer`、`kill`、`teardown`。

**owner 销毁**：job 活着时 `handle.dispose()`，嵌套工具体的 signal 被中止，`job/settled` 为 `status: killed, cause: teardown`。

**审批**：

- 没有开着的回合时（探针直接调），`ask` 被审批服务拒绝：`approval.request() outside an open turn: the approval/asked + approval/decided audit pair must be turn-enclosed ...`。前台直接调 `probe_ask` 和后台调同一个得到同样的错误，后台这个 job 记为 `failed`，`detail` 就是这句，完成通知里也带它。这是探针不在回合里造成的，不是后台特有。
- 在会话日志里手工追加 `turn/start`（不经模型）并给 `approval/request` 挂一个 600 ms 后回答 `allowed-once` 的应答器：前台调用 609 ms 后返回 `probe_ask ran`；后台调用在 `background_run` 返回后立刻 `turn/end`，应答 600 ms 后才到：job 照常 `completed`，`job_output` → `probe_ask ran\n[status: completed]`。会话事件顺序：`approval/asked`（回合内）→ `turn/end` → `approval/decided`（回合外）。宿主没有拒绝回合外追加这条审计事件，但宿主文档说这种形状是“崩溃尾部垃圾”，**重新加载这样的会话是否有问题没有验证**（见开放问题）。

**skill 与提示**：`skill {name: "dsh-background"}` 返回 `<skill_content name="dsh-background">` 加正文，没有错误；用 `systemPrompt.assemble({agent, scope: agent})` 组装出的提示里有这一段，位置在 `tool:web_search` 之前（排序 `TOOL_JOBS + 5`）：

> `background_run(tool, arguments, description) runs one other tool call in the background and returns a job id at once; a completion notice tells you when it is done, then read the result with job_output. Use it for a slow call you do not need yet, so the user can keep talking to you; otherwise call the tool directly. See the dsh-background skill.`

### web profile（rc.5，`cordis` preset 建的 agent）

`dsh --profile web --no-open --port 3401`，探针同样跑 `ctx.agents.create` + `agentPresets.mount(cordis)`。

- 该 agent 的工具列表共 39 个，含 `background_run`、`job_output`、`job_list`、`job_kill`、`bash`、`subagent`、`workflow`。
- 同一套场景（起 job、等、kill、拒绝清单、并发上限、skill、提示段）结果与 headless 一致；`s7` 第五个同样被拒。
- 没有 preset 的裸 agent 只看到全局工具（`background_run` 在内，但没有 `job_*`，因为 web profile 的 `tool-jobs` 在 preset 里挂载），这时 `background_run` 会因为 `jobs.start` 找不到服务该 owner 的 controller 而报错。
- web profile 里审批应答器是界面，探针的审批回合模拟会一直等人，所以那一项在 web 里跳过（`BG_PROBE_SKIP=s11`）。

## 3. 阶段二：自动转后台三问

目标做法：加一个 `tools/execute` 包装，前台调用超过阈值还没结束，就把仍在运行的 `next()` 转成 job，先给模型返回占位结果。实验用探针注册的包装层在 300 ms 后提前返回，让 `next()` 继续跑（`probe/phase2/`，输出 `logs/phase2-rc5.json`）。

**问题 1：step 结束时宿主会不会 abort 调用方 signal？**

- 读源码：调用方 signal 是 agent loop 每个回合的 `phase.abort.signal`（`core/agent-loop/src/agent.ts`）。只有 `cancel()`（用户停止、销毁）会 abort 它（第 180 行）；回合或 step 正常结束时换新的 controller，不 abort 旧的。所以**正常结束不会杀**转入后台的工作。
- 但 `ToolRuntime.dispatchToolBody` 总是把调用方 signal 重新融合进工具体收到的 signal（`fuseToolSignals`），包装层换掉 `exec.signal` 也一样。
- 实验 E3：包装层提前返回、调用方 800 ms 后 abort：工具体的 signal 在同一时刻被中止（`signalAbortedAt` = 14927，`endedAt` = 14927）。E4：包装层把 `exec.signal` 换成自己永不 abort 的 controller 的 signal，结果相同。对照 E5（不 abort）：工具体跑到结束。
- 结论：**不满足**。用户点停止会把转入后台的工作一起杀掉。

**问题 2：占位结果会不会被输出 schema 校验拒绝？**

- E1（工具输出 schema 是 string）：包装层返回 `{isError: false, value: 'PLACEHOLDER-...', content: [{text: 'PLACEHOLDER content from wrapper'}]}` → 结果文本是 `rendered:PLACEHOLDER-moved-to-background`，即**包装层给的 content 被丢弃**，由目标工具自己的 `render` 从 `value` 重新生成。
- E2a（输出 schema 是对象，占位值是字符串）：`isError: true`，`code: INVALID_TOOL_OUTPUT`，`Error: tool "p2_obj" returned invalid output: "value" must be an object`。
- E2b（占位值满足对象 schema）：通过，文本由目标工具的 `render` 生成。
- E2c（占位是 `isError: true` 的结果）：原样放行，文本 `Error: moved to background (placeholder)`。
- 结论：**不满足**。占位值必须满足每个目标工具各自的输出 schema，通用占位只能做成一个错误结果，模型会把它当失败。

**问题 3：宿主会不会等 body 的 promise？**

- 不会：E1 里 `ctx.tools.execute` 在 306 ms 返回，工具体到 5592 ms 才结束；`tools/result` 只触发一次，是占位。**这一项满足。**
- 但抛下的 `next()` 在工具结束时 **reject**：`TypeError: Cannot assign to read only property 'signal' of object` 来自 `dispatchToolBody` 的 `finally { exec.signal = wrapperSignal }`——此时 exec 已被 `notifyResult` 冻结。每一次提前返回的实验（E1 到 E5）都是这样。也就是说真正的工具结果拿不到，转成 job 的 `done` 永远只能得到 reject。

**决定**：不实现自动转后台，也没有开关。README 的“已知限制”写了原因。如果以后宿主让 `next()` 在冻结后仍能正常结算、并给包装层一个替换结果的通道（或让调用方 signal 可以被脱钩），再重做。一个可行的替代是“从一开始就在包装层里用自己的 controller 跑嵌套调用，超时再放弃等待”，但那会让 pre-execute / post-execute 对同一次调用各跑两遍（审批会问两次），这一阶段没有做。

## 4. 0.2.0-rc.2

源码对照（`harness-0.2.0-rc.2` 与 `harness-0.2.1-rc.5`）：本插件用到的接口都在：`ctx.jobs.start/list`、`JobSpec`（kind/label/owner/outputLimitBytes/run）、`JobHandle.append/updateProgress`、`JobOutcome`、`ToolRuntime.get/register/execute`、`ToolExecutionInput.rootCallId`、`ToolArgsError`、`validateJsonSchemaValue`、`defineTool` 的 `presentCall/presentResult`、`systemPrompt.getSectionOrder('TOOL_JOBS')`、`skills.registerProvider`、`fuseToolSignals`、`tool-jobs`。差异只有：rc.2 的 `JobSpec` 类型没有 `toolCall`（运行时被 `jobs-local` 忽略）、id 是 `<kind>-N`、不写 `job/registered` / `job/settled`。

真实宿主：`npm i @deepseek-ai/dsh@0.2.0-rc.2`，同一个 tgz 和同一个探针。因为 peer 范围原来不含 rc.2，安装先被拒绝，用 `dsh plugin --profile headless allow-version @anweat/dsh-background@0.1.0 --dsh-version 0.2.0-rc.2 --accept-risk`（只在 scratchpad 的 `DSH_HOME` 里）放行。结果：除上面三项差异外与 rc.5 一致：

> `probe_sleep started in the background as job tool-1 (sleep 1.5s (alpha)). A completion notice arrives when it finishes; ...`
> `(no new output)\n[status: killed, probe kill]`、并发上限第五个被拒、拒绝清单、skill 和提示段都在、会话销毁后工具体被中止、`background job tool-10 (tool: probe_sleep: finishes unattended) finished [status: completed]. Read its output with job_output.`

据此把 peer 范围放宽为 `>=0.2.0-rc.2 <0.2.1-0 || >=0.2.1-rc.2 <0.2.2-0`（`test:peers` 检查两种解析模式）。把握：0.2.0-rc.2 高（读了类型和实现，且真实宿主跑过）；0.2.1-rc.2 ~ rc.4 中高（只靠“这些包之间没有接口变化”的源码对照，没有单独跑）。

## 5. 单元测试

`pnpm run verify`（typecheck、`test:peers`、build、33 项单测）通过；单测使用宿主真实的 `ToolRuntime` 与 `SystemPrompt`，`ctx.jobs` 用最小假注册表。覆盖前置拒绝、结果映射、截断、图片占位、kill、与回合 signal 脱钩、pre-execute 拒绝和无审批通道、插件卸载（工具被注销、嵌套调用被中止、可重新加载）、skill 与提示段的可选注册。

## 偏离 brief 与理由

1. 工具返回文字：把“Its result arrives with the completion notice”改成“A completion notice arrives when it finishes; read the result with job_output”。真实宿主里通知不带结果，原文会让模型以为通知里就有结果。
2. 前置校验多做了一项：用目标工具自己的参数 schema 校验 `arguments`，错误当场返回给模型，不登记一个马上失败的 job。
3. `nativeBackgroundTools` 之外，目标参数里本来就有 `run_in_background` 的工具也被拒绝（第三方工具自带后台参数时也不重复包装）。
4. 构建只用 `tsc`，没有 tsdown：本插件没有客户端 bundle，不需要。
5. peer 范围放宽到 0.2.0-rc.2（brief 允许，条件是验证过，已验证）。

## 没有验证的部分

- 没有跑模型会话：完成通知唤醒空闲会话的 follow-up turn、`maxConsecutiveWakes` 的影响、模型是否会正确选用 `background_run`、skill 与提示的实际效果。
- 没有看客户端界面怎么展示 `background_run`（`presentCall` 用 generic 卡片）与后台 job。
- 没有测 PTC 模式。
- 没有测 HMR 热卸载的真实路径（headless 里 HMR 关着），卸载行为只在单测里验证（真实 `ToolRuntime` 上 `fiber.dispose()`）。
- 没有测 Windows。

## 开放问题

1. 回合结束后才回答的审批会让 `approval/decided` 落在 `turn/end` 之后。重新加载这样的会话是否有问题？需要在真实模型会话里：让模型 `background_run` 一个会触发审批的工具，回合结束后再点允许，然后重载该会话。
2. 回合已结束、用户很久不回答审批时，嵌套调用一直挂着，占一个 `maxConcurrentJobs` 名额；用户可以 `job_kill`，但这种状态在界面里怎么呈现没有看。
3. 是否要把 `ask_user_question` 之类需要人回答的工具默认放进 `denyTools`？现在只在 skill 里写了不要这么做。
