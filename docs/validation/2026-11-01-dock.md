# 2026-11-01 验证：dock 按钮、私有 RPC 通道、插件页设置（分支 `feat/dock`）

结论：在 `@deepseek-ai/dsh@0.2.1-rc.5` 的真实 Web 客户端里，dock 按钮从头到尾可用：发消息，输入框上方出现带计时的一行，点 **转入后台** 或 **打断**，聊天里出现占位结果，模型约 50 到 60 ms 后发出下一次请求，后台任务区出现任务，任务完成后唤醒轮次，**停止** 按钮能杀掉后台任务。插件页的设置卡片能改前台工具控制、插话策略，改完立刻生效，不重载插件。只在 Web 上验证，Desktop 没有。

执行者是开发者侧代理，不是独立验证者。**没有真实模型**：用的是本机回环上的脚本化端点（key 是字面量 `mock-key`，回放事先写好的“调用工具”和“文字”回复），agent loop、客户端、宿主都是真的。截图和日志在 作者本机的实验目录 `research/experiments/dsh-background-dock-2026-10-31/`（不在本仓库）（`shots/`、`logs/`、`scripts/`）。

## 宿主侧研究的结论

- **私有 RPC 通道**：用 `connection.rpc.handle('/dsh-background', handler)`（同 dsh-web-search-pro、dsh-browser）。处理器签名是 `(endpoint, payload, signal, peer)`。
- **会话身份**：宿主的 RPC 层**不提供**“浏览器正在看哪个会话”。`peer` 只带 `principal`（登录的浏览器共用 owner Peer，`principal.kind === 'owner'`）。所以没有可复用的会话身份，`sessionId` 放进请求，服务端做三件事：principal 必须是 `owner`；`sessionId` 必须对应一个存在的 agent（`ctx.agents.get`）；调用和任务只在这个会话里查找（别的会话的 callId 在这里就是“未知调用”，别的会话的 job 被宿主 `jobs.get(id, caller)` 的 owner 围栏挡掉）。
- **推送还是轮询**：宿主的 Remote 流（`job.list`、`job.follow`）属于类型化网关，插件的私有通道只有一元 RPC。后台任务有现成的推送：客户端 `ctx.jobs`（`job.list` 流的名册和人类 kill），所以 dock 的“后台任务”区直接用它，不轮询，**停止**也走宿主的 `jobs.kill`。前台调用没有推送，只在会话忙且 dock 可用时每秒轮询 `calls`。因此服务端的 `jobs`、`killJob` 端点（任务名册、停止）有实现、有单测，但当前界面不用。
- **槽位**：`conversation.input.dock`（session 作用域的 list 槽，渲染在输入框卡片上方；待办面板 order 0，待发队列 order 20）。`conversation.composer.dock` 在输入框下方（统计药丸用），不合适。dock 注册为 `id: 'background'`、`order: 10`，几何和样式照抄 QueueDock（同样的宽度、3px 嵌入输入卡片、面板材质），用宿主的 `--dsw-*` 令牌，明暗主题都对。
- **插件页设置**：宿主只为 `.volatile()` 字段生成设置表单；外部 bundle 没有默认表单，必须自己在 `plugins.row.config`（键 `@anweat/dsh-background#background`）注册内容。宿主把配置值和 `mutate` 通过 `form` 属性传进来。所以：把 `foregroundControl`、`onUserMessageWhileToolRuns`、`toolPolicies`、`autoBackgroundAfterMs` 标成 `volatile`；配置在 Loader 下是 `Volatile<T>` 引用（`.get()`），插件改为按需读取（`liveConfig`），包装一直安装，`foregroundControl` 关着时直接放行。默认的设置页对这个插件什么都不渲染（没有“配置”入口），所以需要这个小卡片，而不是“保持默认”。
- **Desktop 与 Web**：Web 的客户端模块由 `/plugins` 路由提供，Desktop 用 shell 自带的载体（`fetchBundle()`）派发同样的 bundle 响应。本包的客户端 bundle 与 dsh-browser 同形（CJS、`window.__ModuleLoader__.load` 外壳、模块表外部依赖），按文档应当两边一样加载，但**没有在 Desktop 上验证**。服务端通道注册沿用兄弟插件的写法 `inject(['connection', 'webServer'])`；若 Desktop 没有 `webServer`，通道不会注册，客户端 `status` 失败，dock 保持隐藏（安全失败），需要你在 Desktop 上确认。

## 真实 Web 客户端里看到的

环境：`dsh --profile dock --no-open --port 3402`（web 模板 + 本插件 tgz + 一个只注册 `tr_slow` 的工具插件），`DEEPSEEK_BASE_URL=http://127.0.0.1:18772/v1`，Playwright 驱动系统 Chrome（无头，1100x900，亮色；暗色另截）。控制台错误 0，HTTP 4xx/5xx 0。

**dock 行**（`shots/01-dock-running-row.png`、`01b-dock-row-closeup.png`；暗色 `card-dark-0-row.png`）：发送“请运行慢工具 A”后出现，行文字原样是：

> `tr_slow | {"ms":20000,"tag":"A"} | 0:04 | 转入后台 | 打断`

计时每秒跳一次（探针读到 `0:02` 然后 `0:04`）。按钮是宿主的 `Button`（`sm`、`ghost`），状态点是宿主的 `StateDot`。

**转入后台**（`02-after-transfer-background-section.png`、`03-placeholder-card-in-chat.png`）：点击后 63 ms 模型端点收到下一次请求，最后一条 user 消息是 `tool_result`（`is_error:true`）：`Not a failure, do not retry: tr_slow was moved to the background as job tool-5d4439290cf24054 at the user's request; a completion notice arrives when it finishes, read the result with job_output.`。dock 变成：

> `后台任务 · 1 个运行中 | tr_slow: {"ms":20000,"tag":"A"} | running tr_slow | 运行中 | 0:00 | 停止`

宿主自己的会话头部也同时出现“1 个后台任务运行中”（`ui-jobs`），两处是同一份名册。任务完成后（`04-job-completed-and-wake-turn.png`）：

> `后台任务 | tr_slow: {"ms":20000,"tag":"A"} | 已完成 | 0:14`

完成通知唤醒空闲会话，模型第 3 次请求的内容是 `background job tool-5d4439290cf24054 (tool: tr_slow: {"ms":20000,"tag":"A"}) finished [status: completed]. Read its output with job_output.`，聊天里出现 `A finished. Thanks for the notice.`。（任务计时 0:14 是从转入那一刻起算的，不是从工具开始。）

**占位卡片长什么样**（`card-light-1c-call-open.png`、`card-dark-1c-call-open.png`）：聊天把整个工具调用折叠成“已完成，用时 2 秒 ⌄”，展开后是“已调用工具”，再展开是“工具调用”卡片：标题行和输出区的占位文字都是**红色错误样式**（宿主按 `isError` 渲染），输入区显示 `{"ms": 20000, "tag": "A"}`，页面文本里还有一个“失败”标签。这就是 R2：占位只能是错误形态，客户端不能改样式（本插件没有试图改）。文字本身写明“不是失败，不要重试”，所以对模型是清楚的，对用户界面有点吓人。

**打断**（`05-dock-running-row-B.png`、`06-after-interrupt-chat.png`）：点击后 53 ms 下一次请求发出，最后一条是 `tool_result`（`is_error:true`）`Interrupted by the user: tr_slow was cancelled at the user's request before it finished. It did not complete; run it again only if the user asks.`；工具体在点击时被中止（工具事件日志里 `B aborted`），聊天出现 `B was interrupted, so I moved on without it.`，turn 没有被取消，dock 的前台行消失。

**停止**（`07-background-section-with-stop.png`、`08-after-stop.png`）：C（120000 ms）转入后台，后台任务区同时列出运行中的 C 和已完成的 A（灰色）。点 **停止**：任务变成

> `tr_slow: {"ms":120000,"tag":"C"} | cancelled by the user | 已取消 | 0:01`

工具体被中止（`C aborted`）。随后宿主发了完成通知 `background job tool-205e2da3aa8141bf (tool: tr_slow: {"ms":120000,"tag":"C"}) finished [status: killed, cancelled by the user]. Read its output with job_output.`，**这条通知唤醒了模型**（第 8 次请求）。也就是说用户自己点“停止”也会花掉一轮模型调用，见开放问题。

**插件页设置卡片**（`settings-3-card-initial.png`、`settings-4-policy-background.png`）：在 插件 → `@anweat/dsh-background` → 点组件行，页面上有 4 项：

> `前台工具控制`（开关）· `用户插话时`（`等工具跑完（默认）` / `把工具转入后台，模型立刻继续` / `打断工具，模型立刻继续`）· `按工具设置`（JSON）· `自动转入后台（毫秒）`；底注 `修改立即生效，不需要重启插件；已经在运行的工具不受影响。`

把“用户插话时”改成“把工具转入后台”，profile 的 `cordis.patch.yml` 立刻多了 `background: config: {foregroundControl: true, onUserMessageWhileToolRuns: background}`。然后在会话里工具运行时输入“先别等它，继续说点别的”并按 Cmd+Enter（“插话发送”）：**47 ms 后**下一次模型请求发出，内容是占位 `tool_result` 加 steering 文字，没有点 dock；后台任务区出现任务（`settings-5-steer-moved-to-background.png`）。再把 **前台工具控制** 开关关掉：patch 里变成 `foregroundControl: false`，新一轮里工具运行 5 秒期间 dock 不出现（`settings-7-no-dock-when-off.png`）。**没有发生插件重载**：设置改动时那个已在后台的任务一直跑到完成（工具日志 `A finished`），如果插件重载，卸载时会中止它。

## 单元测试

`pnpm run verify` 通过：typecheck、`test:peers`、build（服务端 `tsc` 加客户端 `tsdown`）、71 项测试（上一阶段 54 项，新增 17 项）、客户端 bundle 检查。新增覆盖：

- RPC（10 项，经真实的插件注册和假的 Host `connection`）：通道注册与卸载、无 connection 时照常加载、`status` 开关/门禁/关闭、非 owner 被拒、`calls` 只列该会话、转入/打断只作用于该会话（别的会话的 callId 是未知调用）、未知会话/错误载荷/未知端点、关闭和门禁时拒绝并给原因、`jobs`/`killJob` 只涉及本插件的该会话任务（跨会话 kill 被拒、reason `stopped by the user`）。
- 客户端控制器（6 项）：词典键一致、`status` 只问一次且失败时保持隐藏、轮询只在有人观看时运行、停止后不再轮询、服务端时钟偏移、`act` 的载荷/待处理/拒绝提示/刷新、设置解析器。
- 配置（1 项新增，另 1 项改写）：volatile 引用与普通值一样被读取；改写的那项验证设置在运行中切换后，下一个调用立刻按新值处理。

React 组件本身没有单测（节点里没有 DOM 环境，宿主 primitives 带 CSS 模块），靠上面的真实浏览器验证。

## 偏离与限制

1. **设置**：任务书说“默认表单若能渲染就不做自定义卡片”。实测默认什么都不渲染（外部 bundle 没有默认表单，且宿主只为 volatile 字段生成表单），所以做了一个小卡片，并把这四项改成 volatile、插件改成实时读取（`foregroundControl` 关闭时包装放行，而不是不安装）。`Config` 的 TypeScript 类型因此带 `Volatile<…>`，导出的 schema 标成 `z<any>`（否则声明文件要引用传递依赖）。
2. **后台任务区的数据和停止**走宿主的 `ctx.jobs`（推送、人类 kill），没有用本插件的 `jobs`/`killJob` 端点；端点保留并有测试，给没有宿主任务流的客户端用。
3. 客户端注入需要 `jobs` 服务（`inject` 里写了）；宿主没有它时客户端插件不会激活。
4. 面板里的任务计时从转入时刻起算；已结束任务只留最近 3 个，完整历史在宿主自己的任务列表里。

## 开放问题

1. **用户点“停止”会唤醒模型**：宿主把人类 kill 的完成通知当成普通通知，空闲会话被 follow-up 唤醒，模型花一轮去回应一个用户自己发起的取消。可以用 `tool-jobs` 的 `completionDelivery: quiet`，但那会影响所有完成通知；更好的办法是宿主区分人类 kill。
2. **占位的错误样式**（R2）：卡片红色加“失败”标签，只能靠宿主客户端改。
3. **Desktop 未验证**：客户端模块加载、`inject(['connection','webServer'])` 在 Desktop 上是否可用、dock 槽位渲染。
4. 窄屏、键盘操作、子 agent 会话里的 dock、同时显示多个会话的布局都没测；只有中英两套文案。
5. 忙时回车默认是排队，不触发插话策略；设置卡片的提示写了这一点，但用户不改习惯就用不上。dock 按钮不受影响。
6. 前台行 1 秒轮询：转入或打断之后立刻刷新一次，但别的原因（工具自己结束）最多晚 1 秒才从 dock 消失；dock 行的计时是客户端时钟加服务端偏移，已按偏移修正。
